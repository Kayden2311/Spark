# Startup promotion and campaign schema extension

Status: proposed schema only. The user confirmed that promotion includes both subscription discounts and paid startup advertising. This extends [database schema](database-schema.md); it implements neither billing nor advertising.

## Product model

A promotion plan sells a fixed placement for a fixed number of days at a fixed price. It does not promise exclusive inventory, minimum impressions, ranking fairness or clicks. Each placement is a nonexclusive sponsored pool. CPM/CPC billing, auctions and exclusive inventory are outside this initial model. Subscription discounts and advertising are distinct products; existing promotions/promotion_prices only apply to subscription prices. No advertising coupons are implied.

The advertiser is a workspace. Its campaign targets a public, nonarchived community owned by that same workspace. An approved creative contains a headline, plain-text description and internal community link. Uploads and arbitrary external landing URLs remain out of scope. Sponsored results are labeled and their selection cannot bypass community visibility rules.

Fields use the parent document's UUID, timestamps, nullable notation, tenant-qualified FKs, money and deletion rules. Catalog and moderation records are restricted, with explicit public catalog/creative projections.

No permanent viewer IDs or raw IP addresses are needed for aggregate campaign analytics. Counters are approximate and may include repeats/bots unless a later measurement story specifies deduplication and abuse resistance. Do not present counts as verified unique reach.

Platform campaign review uses separately provisioned staff identities. A restricted global `platform_role_assignments` table has `user_id`, `role text`, `granted_by_user_id`, `revoked_at timestamptz?`, and shared timestamps; use `id` PK with partial UNIQUE (user_id,role) while unrevoked. Role is campaign_moderator for this slice. User IDs reference global users. Provisioning uses an administrative adapter, never workspace APIs or self-service membership. Initial staff bootstrap is an explicit deployment operation, not a hidden default admin. Review use cases check current unrevoked role, active account and record reviewer. Reject self-review when reviewer is a member of the advertiser workspace.

## State and payment invariants

1. Workspace owner/admin edits drafts and submits. Submission increments version and sets pending. A moderator decision is append-only for the submitted version; approved_version equals that version. Editing approved content increments version, clears approval and pauses delivery pending a fresh review. Audit every state change.
2. Campaign purchase snapshots immutable plan placement, duration, amount and currency; constraints/use-case validation verify campaign placement matches purchased plan. Reserve a single live order using campaign lock and partial uniqueness. Provider checkout creation is outside transaction with stable idempotency key. Resolve uncertain provider outcomes before releasing/replacing the pending order, preventing two successful charges.
3. Reuse the restricted payment_events inbox from the parent design. Signature verification and server-side provider ID resolution precede processing. Link order by stored checkout/payment IDs, never client-supplied tenant. Verify expected amount/currency before marking paid. Inbox completion and order update commit atomically; duplicates and out-of-order events reconcile with authoritative provider state.
4. Scheduling requires approved current version, paid order, active workspace and public nonarchived target. Set starts_at to max(requested_start_at, activation time) and ends_at to starts_at plus purchased duration_days in UTC. Persist these times once; retries never extend the period. Copy uses exact fixed UTC days, not local recurring days. Duration is wall-clock; pauses do not automatically extend it.
5. Every sponsored read rechecks current approval/version, paid order, active workspace, current public target, current placement availability, delivery state and time interval. Do not rely on a scheduler updating active/completed flags. Paused/cancelled campaigns and hidden/archived targets are immediately ineligible even if cached. Cache invalidation and TTL must be designed before caching is implemented.
6. Rejection before payment incurs no charge. Payment followed by rejection or inability to activate triggers refund_pending and a billing reconciliation job. Paid cancellation pauses delivery immediately and records request; refund amount/eligibility is an unresolved commercial policy that must be selected before selling campaigns. Never claim a refund until provider confirms it. Retain orders/invoices/reviews after cancellation or workspace archive.
7. First version offers no order upgrades, partial refunds, extensions or automatic renewals. Those require versioned commercial rules and additional ledger records. Failed/cancelled orders may retry only after provider reconciliation and only before any paid activation. A campaign whose order is refunded is terminal and cannot be repurchased or reactivated; a new purchase requires a new campaign with fresh review and its own immutable interval. Payment processing marks the refunded campaign cancelled transactionally. Purchase admission locks the campaign and rejects it if any historical order is refunded or any activation interval already exists.

The database cannot enforce elapsed-time visibility with a static CHECK constraint; live sponsored selection must apply interval and state predicates. Cross-table approval/order/target rules need transaction checks and reviewed enforcement triggers where appropriate. A parent community becoming private must suppress selection regardless of campaign row state.

## Authorization, indexes and checks

Tenant campaign/order/metrics reads require active workspace owner/admin; only approved creative projection is public. Billing and reviews use dedicated roles. FORCE RLS and tenant-qualified FKs follow the parent contract. Platform moderator access does not grant unrelated tenant content access. Raw provider data stays in the restricted inbox.

Initial indexes: promotion_campaigns (tenant_id,created_at,id); promotion_campaigns (placement_id,starts_at,ends_at,id) for approved scheduled/active candidates; promotion_campaigns (review_status,created_at,id) for staff queue; promotion_orders (tenant_id,campaign_id); promotion_reviews (tenant_id,campaign_id,campaign_version); all remaining FK-leading indexes as needed. Public predicates use current time at query execution, not in partial indexes.

Before implementation verify same-tenant target and matching plan placement/currency/provider; repeated checkout and webhook delivery; stale approval after edits; moderator self-review/role revocation; scheduler delay; hidden/archived target suppression; duplicate activation not extending dates; refusal to repurchase refunded/previously activated campaigns; fresh reviewed campaign required for a new purchase; payment without approval; cancellation/refund reconciliation; tenant RLS and pooled connection reuse. No such runtime tests have run for this proposal.
