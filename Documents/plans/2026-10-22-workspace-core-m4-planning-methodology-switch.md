# Workspace core M4 — Planning objects and methodology switch Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Teams plan the way their methodology works — Scrum teams plan, start and complete sprints from a backlog; Waterfall teams edit phases and milestones and re-baseline; every team edits its board columns and WIP limits — and an owner, admin or project lead can switch a project's methodology later without losing history.

**Architecture:** Three migrations add SECURITY DEFINER `spark.ws_*` writes for sprints (0023), phases/milestones/baselines (0024) and statuses plus the methodology switch (0025), all under the existing lock order and change-set rules. Fastify routes in `src/routes/workspace/planning.ts` expose them. The project area gains three tabs — Backlog (Scrum), Timeline (Waterfall) and Settings (board columns, WIP and the switch wizard) — next to M3's Board and Overview.

**Tech Stack:** PostgreSQL 18 (hand-written SQL migrations), Fastify 5 JSON-schema routes, pg, Vitest; Next.js 16.3 / React 19 client components, plain CSS, Vitest + Testing Library.

**Spec:** `Documents/product/workspace-core-design.md` — "Methodology templates", "Methodology switching (user requirement)", milestone **M4**. M2 plan (`Documents/plans/2026-10-18-workspace-core-m2-projects-methodology.md`) and M3 plan (`Documents/plans/2026-10-19-workspace-core-m3-tasks-board.md`) for the conventions already in place. Migration numbers in the spec are indicative; **M4 uses `0023`–`0025`**.

## Global Constraints

- English only in code, copy, docs, commits.
- REST rules (`rest-clean-compliance.md`): problem+json via `problem()`; `Cache-Control: private, no-store` on authenticated responses; 201 + `Location` + `ETag` on create; `If-Match` required on PATCH and on the state-changing commands start/complete/baseline/methodology (missing → 428, malformed → 400 `invalid_if_match`, stale → 412 `version_mismatch` with `current`); origin guard on non-GET; schemas `additionalProperties: false` and rejected unknown keys.
- Writes are `spark.ws_*`: `LANGUAGE plpgsql SECURITY DEFINER SET search_path = ''`, `REVOKE ALL … FROM PUBLIC`, `GRANT EXECUTE … TO spark_app`; actor = `spark.require_session_actor()`; non-members → `not_found` before any other outcome (including 22023 validation); members lacking authority → `forbidden`. Input violations raise ERRCODE `22023` with a whitelisted message.
- **Authority:** creating, editing, starting and completing sprints; editing phases and milestones; re-baselining; editing statuses; switching methodology — workspace `owner|admin` or the project's current lead. Assigning an issue to a sprint or phase stays an ordinary issue edit any active member may make (`ws_update_issue`).
- **Lock order:** workspace row `FOR SHARE` (`spark.lock_workspace_member`) → project `FOR UPDATE` → board → statuses (by id) → sprints (by id) → phases/milestones (by position/id) → issues (by id). Never take the workspace row `FOR UPDATE` in these writes.
- **Issue change sets:** every issue whose row changes gets `version + 1`, one `issue_events` row (`issue.updated`, `changes.fields` listing what moved: `sprintId`, `statusId`, `phaseId`) and one processed `outbox_events` row, in the same transaction (deferred `check_issue_change_set`). Bulk moves (carry-over, switch remap) lock issues by id first.
- **Sprints:** name trimmed 1–80; goal ≤ 500; dates required to start (`starts_at < ends_at`, length 1–28 days; default length = `projects.sprint_length_days`); at most one `active` sprint per project (existing partial unique index); only `planned` sprints are editable for dates; completed/cancelled sprints are history; `version` bumped by every write. Sprint writes only for Scrum projects (`Invalid methodology` otherwise, 22023).
- **Start:** `planned` → `active`, `started_at = now()`, snapshot every non-archived issue in the sprint into `sprint_commitments` (append-only) with its story points, set `committed_points`/`committed_count`; in-app notification kind `sprint_started` to each distinct assignee of a committed issue other than the actor (title `"<project name>: <sprint name> started"`). Second concurrent start → `already_active`.
- **Complete:** `active` → `completed`, `completed_at = now()`, freeze `completed_points`/`completed_count` from issues in a `done` category; every open issue moves to `p_carry_to` (a `planned` sprint of the same project) or to the backlog (`sprint_id = NULL`) as one change set per issue.
- **Velocity** (frontend): average `completed_points` of the last 3 completed sprints; "No velocity yet" with none.
- **Phases/milestones (Waterfall only):** phase rules from M2 (names 1–60, 1–12 phases, contiguous positions, `planned_start ≤ planned_end`, inside project dates, non-overlapping in order); milestone name 1–80, `due_date` inside project dates, optional `phase_id` of the same project; completing a milestone sets `completed_at`. **Baselines are immutable** except through `ws_rebaseline_project`, which copies planned → baseline for every phase and milestone, sets `projects.baselined_at`, requires a reason (1–200) and writes audit `project.rebaselined`.
- **Statuses:** `ws_update_status` changes name (1–40, unique case-insensitively in the project) and `wipLimit` (NULL or 1–99, never below current occupancy — `guard_status` already raises 23514 "WIP limit is below current occupancy"; the function pre-checks and returns `wip_below_occupancy`). Category of a referenced status cannot change (existing guard).
- **Methodology switch** (spec "Methodology switching"): one transaction in `ws_switch_methodology`. Leaving Scrum requires no active sprint (`active_sprint` outcome; the wizard offers "Complete sprint now"); sprints stay as history. Leaving Waterfall keeps phases/milestones read-only as history; milestones stay usable everywhere. Entering Scrum sets `sprint_length_days` (7–28, default 14) and leaves open issues in the backlog. Entering Waterfall requires start/target dates and a phase plan (M2 phase rules); unphased issues show in an "Unphased" bucket. Entering Kanban proposes the template WIP limits, editable, validated against current occupancy. Columns: the target column list may keep existing statuses (renamed, WIP changed) and add new ones; every status not kept must have a mapping to a target column, every issue in it moves (one change set per issue), then the unreferenced status rows are deleted. Categories of kept referenced statuses cannot change — to change a category, add a new column and map to it. Close the open `project_methodology_periods` row (`ended_at = now()`), open a new one with the reason; `projects.methodology` updated, `settings_version + 1`; audit `project.methodology_switched` `{from, to}`.
- Rate limits: planning writes 30/min (`MUTATION_RATE_LIMIT`); reads only the global limiter.
- Frontend: landing-page visual language and the M2/M3 workspace screens (`globals.css` tokens, `.sparkPrimary`, `.sparkSecondary`, pastel tags, initials avatars, `ws*` classes, methodology accents Scrum `#2563eb`, Kanban `#1baf7a`, Waterfall `#d97706`); no new dependencies; read `Spark_Core/frontend/node_modules/next/dist/docs/` before routes/layouts; every motion off under `prefers-reduced-motion`; keyboard and phone (390 px) alternatives for every drag.
- Commands — backend (`Spark_Core/backend`): `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:database`, `pnpm build`, `pnpm db:migrate`. Frontend (`Spark_Core/frontend`): `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`. Never report an unrun check as passing.

`22023` whitelist additions (`KNOWN_INPUT_ERRORS` in `src/routes/workspace/guard.ts`): `Invalid sprint name`, `Invalid sprint goal`, `Invalid sprint dates`, `Invalid sprint`, `Invalid phase`, `Invalid milestone`, `Invalid baseline reason`, `Invalid status name`, `Invalid WIP limit`, `Invalid status mapping`, `Invalid switch reason`, `Invalid methodology` (exists), `Invalid project dates` (exists), `Invalid sprint length` (exists), `Invalid project phases` (exists).

## Review Focus

1. Two leads press "Start sprint" at the same time (or start while another sprint is active) → exactly one active sprint; the other gets 409 `sprint_already_active` with a clear message → DB concurrency test (Task 1), route test (Task 4).
2. Completing a sprint with unfinished work → every open issue lands in the chosen next sprint or the backlog with a new version, event and outbox row; completed totals frozen and never change afterwards → DB test (Task 1), FE test (Task 5).
3. Switching Kanban → Scrum → Waterfall → Kanban on a project with issues → every issue keeps a valid status in the same project, periods form an unbroken history, and no issue loses its sprint/phase history silently → DB tests for all six directions (Task 3).
4. Lowering a WIP limit below the number of cards in that column (in Settings or in the switch wizard) → refused with "N cards are in this column; the limit can't be below that" and nothing saved → DB test (Task 3), FE test (Task 7).
5. A plain member opens Backlog, Timeline or Settings → can see the plan but every planning control is hidden or disabled with "Only owners, admins and the project lead can change the plan"; the API refuses with 403 if called directly → route tests (Task 4), FE tests (Tasks 5–7).
