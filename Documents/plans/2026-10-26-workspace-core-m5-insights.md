> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every workspace member can see how a project is doing against its plan — done vs plan with a forecast, completion by member, flow over time — plus the charts that fit the project's methodology (Scrum burndown and velocity, Kanban flow, cycle time and aging work, Waterfall phases against their baseline and milestones), across methodology switches; and a workspace page shows every project, every member's completion and the team's activity.

**Architecture:** Analytics are computed on read. Migration `0026` adds read-only `spark.insight_*` SQL functions (SECURITY INVOKER, so RLS still applies) that replay the `issue_events` `after` snapshots into per-day states; the simple current-state reads (aging, cycle times, schedule, overdue) stay as route SQL. Pure rules — unit choice, plan %, plan status, forecast, ideal burndown line, commitment reliability, scope creep, milestone state, variance — live in `src/modules/work/domain/metrics.ts`. Fastify routes in `src/routes/workspace/insights.ts`. A local-only seed builds a realistic multi-project workspace so the charts, the EXPLAIN measurements (optional index migration `0027`) and the E2E have data. The frontend adds an Insights tab per project and a workspace Insights page, with two new viz components.

**Tech Stack:** PostgreSQL 18 (hand-written SQL migrations), Fastify 5 JSON-schema routes, pg, Vitest; Next.js 16.3 / React 19 client components, recharts 3 (existing), plain CSS, Vitest + Testing Library.

**Spec:** `Documents/product/workspace-core-design.md` — "Cross-cutting decisions" (analytics on read, ranges 7–180 days, UTC buckets, the `issue_events(tenant_id, project_id, created_at, issue_id)` index — **already created in 0019**), "Methodology templates" (metrics table and "Common to all"), "Metrics across a switch", milestone **M5**. ## Global Constraints

- English only in code, copy, docs, commits.
- REST rules (`rest-clean-compliance.md`): every insights route is `GET`, authenticated, `Cache-Control: private, no-store` on success and errors, problem+json via `problem()`, query schemas `additionalProperties: false` (unknown query keys → 400). Non-members and unknown ids → uniform 404 (`not_found`); there is **no** extra role gate — insights, including member stats, are visible to every active workspace member (user decision in the spec).
- Reads run inside `guard.run` (session-bound transaction, `statement_timeout = 5s` already set there) with explicit `tenant_id` **and** `project_id` filters in every statement, on top of RLS. The route first resolves the project (or sprint, or workspace) through RLS; only then does it call the insight functions with the resolved `tenant_id`/`project_id`.
- **Ranges:** `days` query parameter, integer 7–180, default 30. The range is the `days` UTC calendar days ending today (UTC) inclusive: `from = today − (days − 1)`, `to = today`. Day buckets are UTC (`(ts AT TIME ZONE 'UTC')::date`), as in the admin insights. Dates in responses are `YYYY-MM-DD`; instants ISO 8601 UTC.
- **History replay (0026):** an issue's state at instant `t` is the `changes->'after'` snapshot of its event with the highest `to_version` whose `created_at < t` (state "at the end of day d" uses `t = d + 1 day` at 00:00 UTC). Archived issues (`after.archived = true`) are excluded from counts. Events whose `after` has no `category` are ignored (none exist today; defensive). An issue with no event before `t` did not exist at `t`.
- **Done transitions:** an issue "completes" on the day of an event whose `after.category = 'done'` while its previous snapshot's category was not `done` (or it had none). Reopen and re-complete counts again (throughput is flow, not unique issues). "Completed in range" for member stats uses `issues.completed_at` of issues currently in a `done` category and not archived (the guard keeps `completed_at` only while done).
- **Units:** a metric uses story points when at least 80% of the items in its scope have `story_points` set, otherwise counts (spec). Every response that mixes the two carries `unit: "points" | "count"`.
- **Completion toward plan** (`metrics.ts`): `donePercent` = done ÷ total in the unit; `planPercent` = elapsed share of the plan window, clamped 0–100 (`(today − start + 1) ÷ (end − start + 1)` in days); `status` = `on_track` if `donePercent ≥ planPercent − 10`, `at_risk` if `≥ planPercent − 25`, else `behind`; `no_plan` when there is no window. Windows: Scrum → the active sprint and its non-archived issues (no active sprint → `no_plan`, totals over the whole project); Waterfall → project `start_date`–`target_date`, all non-archived issues; Kanban → project dates when both set, else `no_plan`. **Forecast:** remaining ÷ mean daily throughput (same unit) over the last 14 UTC days; `forecastDate = today + ceil(remaining ÷ rate)`; `null` when the rate is 0; `remaining = 0` → `forecastDate = today` with `status` unchanged.
- **Member stats:** grouped by **current** assignee (`null` → "Unassigned", listed last). `completed`/`completedPoints` = issues completed in range; `onTimeRate` = completed-in-range with a due date and `completed_at` UTC day ≤ `due_date`, ÷ completed-in-range with a due date (`null` when none); `open` = non-archived issues not done; `overdue` = open with `due_date < today`; `medianCycleDays` = median of `(completed_at − started_at)` in fractional days over completed-in-range issues that have `started_at` (`percentile_cont(0.5)`, `null` when none). Only active members and "Unassigned" appear; a departed member's work stays under their name if they still hold the assignment (display name from `users` via the coworker policy).
- **Cycle and lead time:** cycle = `completed_at − started_at`, lead = `completed_at − created_at`, in days with one decimal. p50/p85 via `percentile_cont` over all completed-in-range issues; the scatter returns at most 500 most recent points with `truncated: true` beyond that.
- **Aging WIP:** open, non-archived issues in an `in_progress` category; `ageDays = now − started_at` (falls back to `created_at` when `started_at` is null); reference lines are the cycle-time p50/p85 of the last 90 days. Column WIP vs limit: every status with its category, `wipLimit` and current non-archived occupancy (the `guard_status` definition).
- **Scrum:** burndown per sprint over the UTC days `starts_at`…`ends_at` (inclusive; a completed sprint uses its own window; days after today are `null`). Per day: `scope` = sprint issues (non-archived) at end of day, `remaining` = those not done, `ideal` = linear from the committed base at the start day to 0 at the end day. The unit is decided once per sprint from the committed issues (fallback: issues in the sprint now). Velocity: the last 6 completed sprints whose `completed_at` falls in the selected period, oldest first, each with `committedPoints`/`completedPoints` (the frozen M4 columns) and counts. **Commitment reliability** (M4 note: committed issues already done at start): base = committed issues **not** in a done category at `started_at`; reliability = base issues done just before completion (`created_at < completed_at`, the completion change set shares the timestamp) ÷ base, in the sprint's unit; `alreadyDone` = committed issues done at start, reported separately and excluded from both sides; `null` when the base is empty. **Scope creep:** issues in the sprint just before completion that have no commitment row (`added`, count and points) and committed issues no longer in the sprint (`removed`); `creepPercent` = added ÷ base in the unit (`null` when the base is 0).
- **Waterfall:** per phase — `varianceDays = planned_end − baseline_end` (`null` without a baseline), done ÷ total of the phase's non-archived issues (unit rule), `planPercent` over the phase window, status rule above. Project `scheduleVarianceDays` = latest phase `planned_end` − latest `baseline_end`. Milestone state: `hit` = completed on or before `due_date` (UTC day); `missed` = completed after `due_date`, or open with `due_date < today`; `at_risk` = open with `due_date` within today…today + 7; `upcoming` otherwise. Variance colours reuse the M4 ruling (on baseline green, 1–7 d late amber, > 7 d red).
- **Across a switch:** common metrics (summary, members, flow, cycle time, aging, workspace) span full history and ignore methodology. Methodology-specific endpoints (`velocity`, `schedule`) and the frontend's choice of charts take `period` (a `project_methodology_periods.id`, default the open period); unknown or foreign period → 404 `period_not_found`. `GET /projects/{id}/plan` gains `id` on each `periods` item. Flow responses carry `markers` — the period boundaries inside the range (`{ at, from, to }`) — drawn as "Switched Kanban → Scrum on Oct 3" lines.
- Bounds: summary overdue list ≤ 20, workspace overdue ≤ 50, scatter ≤ 500, aging ≤ 200, velocity ≤ 6 sprints. Workspace insights cover non-archived projects only; project insights of an archived project stay readable (M4 ruling on archived reads).
- Rate limits: reads only the global limiter.
- Frontend: landing-page visual language and the M2–M4 workspace screens (`globals.css` tokens, `.sparkPrimary`/`.sparkSecondary`, pastel tags, initials avatars, `ws*` classes, methodology accents Scrum `#2563eb`, Kanban `#1baf7a`, Waterfall `#d97706`); every chart inside `ChartCard` with a legend and its table view (`table` prop); no new dependencies; read `Spark_Core/frontend/node_modules/next/dist/docs/` before routes/layouts; every motion off under `prefers-reduced-motion`; 390 px layout without horizontal page scroll.
- Commands — backend (`Spark_Core/backend`): `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:database`, `pnpm build`, `pnpm db:migrate`. Frontend (`Spark_Core/frontend`): `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`. Never report an unrun check as passing.
