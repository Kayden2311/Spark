# Workspace core M6 — Schedule Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A workspace has a real shared calendar. Any member can schedule an event (stand-up, review, customer call), invite teammates, and answer an invitation; organizers, owners and admins can move or cancel it. The week view also shows the dates the work already implies — tasks due, sprint ends, milestones — so the team sees meetings and deadlines in one place (US-E6).

**Architecture:** One migration (`0027_schedule.sql`) adds SECURITY DEFINER `spark.ws_*` writes for calendar events and attendee responses on the existing `calendar_events`/`event_attendees` tables (already RLS-protected, versioned and membership-keyed since 0000–0014), plus in-app notification kinds. Fastify routes in `src/routes/workspace/schedule.ts` expose the calendar read (events + derived deadlines) and the writes. The frontend replaces the `/schedule` mockup with `/w/[slug]/schedule` (week grid on desktop, agenda on phones), an event dialog and RSVP controls; `/schedule` redirects.

**Tech Stack:** PostgreSQL 18 (hand-written SQL migrations), Fastify 5 JSON-schema routes, pg, Vitest; Next.js 16.3 / React 19 client components, plain CSS, Vitest + Testing Library.

**Spec:** `Documents/product/workspace-core-design.md` — "Cross-cutting decisions" (writes, reads, concurrency, notifications, rate limits) and milestone **M6 — Schedule**. Conventions: M4 plan (`2026-10-22-workspace-core-m4-planning-methodology-switch.md`) and M5 plan (`2026-10-26-workspace-core-m5-insights.md`). Migration numbers in the spec are indicative; **M6 uses `0027`**. Reminders stay deferred (spec: "Reminders deferred"; the daily due-soon email is M7).

## Global Constraints

- English only in code, copy, docs, commits.
- REST rules (`rest-clean-compliance.md`): problem+json via `problem()`; `Cache-Control: private, no-store` on authenticated responses (success and error); 201 + `Location` + `ETag` on create; `If-Match` required on PATCH and on the cancel command (missing → 428, malformed → 400 `invalid_if_match`, stale → 412 `version_mismatch` with `current`); origin guard on non-GET; schemas `additionalProperties: false` and unknown keys rejected; uniform 404 for non-members and unknown ids (`event_not_found`, the workspace routes' existing workspace 404 code).
- Writes are `spark.ws_*`: `LANGUAGE plpgsql SECURITY DEFINER SET search_path = ''`, `REVOKE ALL … FROM PUBLIC`, `GRANT EXECUTE … TO spark_app`; actor = `spark.require_session_actor()`; lock the workspace row `FOR SHARE` via `spark.lock_workspace_member` first, then the event `FOR UPDATE`, then attendee rows by `user_id`; non-members → `not_found` before any other outcome (including 22023 validation); members lacking authority → `forbidden`. Input violations raise ERRCODE `22023` with a whitelisted message.
- **Authority:** any active workspace member may create an event and is its organizer. Editing and cancelling: the organizer, or a workspace `owner|admin`. Responding: only an invited attendee, for themselves. Everyone in the workspace can read every event (events are team-visible; there are no private events in Phase 1).
- **Event fields:** `title` trimmed 1–200; `description` ≤ 2000 (NULL when blank); `location` trimmed ≤ 200 (NULL when blank); `startsAt < endsAt`, both between 2000-01-01 and 2100-12-31, duration 5 minutes to 14 days; `timezone` an IANA name present in `pg_timezone_names` (the zone the organizer scheduled in — used for display and future reminders; instants are stored as `timestamptz`); optional `projectId` (a non-archived project of the same workspace); optional `issueId` (requires `projectId`, an issue of that project — existing DB check); `attendeeUserIds` 0–50 distinct active members of the workspace (the organizer is always an attendee with response `accepted`, whether listed or not).
- **Lifecycle:** `status` `scheduled` → `cancelled` (terminal; a cancelled event is read-only and still listed, shown struck through). `completed` exists in the schema but is not written in M6 (an event in the past is simply past). Every write bumps `calendar_events.version`; attendee responses do not bump the event version (they live on `event_attendees`, `responded_at` set).
- **Attendee changes on update:** `attendeeUserIds` in a PATCH replaces the invited set: kept attendees keep their response; new ones start `pending`; removed ones are deleted (no reminders exist yet — `event_reminders` stays unused). Changing `startsAt`/`endsAt` resets every non-organizer attendee's response to `pending` (they agreed to a different time).
- **Notifications** (in-app only, no email in M6): new kinds `event_invited` (each newly invited attendee except the actor; title `"<actor> invited you to <title>"`), `event_rescheduled` (each attendee except the actor when start/end change; `"<title> moved to <local date/time in the event timezone>"`), `event_cancelled` (each attendee except the actor; `"<title> was cancelled"`). Each notification is inserted in the same transaction with a processed `outbox_events` row (`aggregate_type` `calendar_event`, `aggregate_version` the event version after the write — there is no aggregate-type allowlist, and the issue change-set trigger only applies to `issue`), following the 0021 pattern; `resource_type` `calendar_event`. Extend `notifications_kind_allowed` from the 0023 list.
- **Calendar read:** `GET /workspaces/{workspaceId}/calendar?from&to` with `from`/`to` ISO 8601 instants (`from < to`, span ≤ 62 days; the client computes the bounds of the viewer's local week); returns events overlapping `[from, to)` (scheduled and cancelled) with attendees, plus **derived deadlines** inside the range from non-archived projects: open, non-archived issues with a `due_date` (kind `task_due`), `planned|active` sprints' end (`sprint_end`), and open milestones' `due_date` (`milestone_due`). Dates of deadlines are calendar dates (no time); a deadline is "inside" when its date falls in `[from, to)` interpreted in the `tz` query parameter (IANA, default `UTC`) — validate `tz` like `timezone`. Caps: 500 events, 500 deadlines, each with `truncated`.
- Rate limits: event writes and responses 30/min (`MUTATION_RATE_LIMIT`); the calendar read only the global limiter.
- Frontend: landing-page visual language and the M2–M5 workspace screens (`globals.css` tokens, `.sparkPrimary`/`.sparkSecondary`, pastel tags, initials avatars, `ws*` classes; methodology accents Scrum `#2563eb`, Kanban `#1baf7a`, Waterfall `#d97706`); reuse the mockup's `.weekGrid`/`.eventRow` look; no new dependencies (no date library — use `Intl.DateTimeFormat` and the browser time zone); read `Spark_Core/frontend/node_modules/next/dist/docs/` before routes/layouts; every motion off under `prefers-reduced-motion`; 390 px layout without horizontal page scroll; keyboard-operable dialog and RSVP controls.
- Commands — backend (`Spark_Core/backend`): `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:database`, `pnpm build`, `pnpm db:migrate`. Frontend (`Spark_Core/frontend`): `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`. Never report an unrun check as passing.

`22023` whitelist additions (`KNOWN_INPUT_ERRORS` in `src/routes/workspace/guard.ts`): `Invalid event title`, `Invalid event description`, `Invalid event location`, `Invalid event time`, `Invalid event timezone`, `Invalid event project`, `Invalid event issue`, `Invalid event attendees`, `Invalid event patch`, `Invalid event response`.

## Review Focus

1. A member of workspace B guesses an event id from workspace A → 404 on read, update, cancel and respond; inviting a user who is not an active member of the event's workspace is refused; a removed member can no longer respond → DB tests (Task 1), route tests (Task 2).
2. Two people edit the same event at once → one succeeds, the other gets 412 with the current event and the UI shows "Updated by a teammate" and reloads; cancel uses the same rule → DB test (Task 1), route test (Task 2), FE test (Task 4).
3. Moving an event to another time resets attendees' answers to "pending" and notifies them; cancelling notifies every attendee except the person who cancelled; no notification goes to the actor → DB tests (Task 1).
4. A plain member opens someone else's event → can see it and answer their own invitation, but has no Edit/Cancel; the API refuses with 403 if called directly → route tests (Task 2), FE tests (Task 4).
5. A viewer in Asia/Ho_Chi_Minh and an organizer who scheduled in Europe/Berlin see the same instant at their own local times; a task due date shows on the right day in the viewer's week; an event crossing midnight appears on both days → route tests (Task 2), FE tests (Task 3).

**Interfaces (SQL):**
- `spark.ws_create_event(p_workspace uuid, p_title text, p_description text, p_location text, p_starts timestamptz, p_ends timestamptz, p_timezone text, p_project uuid, p_issue uuid, p_attendees uuid[]) RETURNS TABLE(outcome text, event_id uuid, event_version int)` — outcomes `ok | not_found`; inserts the organizer as an `accepted` attendee plus each invited attendee `pending`; `event_invited` notifications.
- `spark.ws_update_event(p_event uuid, p_expected_version int, p_patch jsonb) RETURNS TABLE(outcome text, event_version int)` — patch keys `title, description, location, startsAt, endsAt, timezone, projectId, issueId, attendeeUserIds` (unknown key → 22023 `Invalid event patch`); outcomes `ok | not_found | forbidden | version_mismatch | cancelled` (a cancelled event cannot change); no-op patch → `ok` without a version bump; attendee and reschedule rules from Global Constraints.

- `spark.ws_respond_event(p_event uuid, p_response text) RETURNS TABLE(outcome text)` — `p_response` in `accepted|declined|tentative` (22023 `Invalid event response` otherwise); outcomes `ok | not_found | not_invited | cancelled`; sets `responded_at`; the organizer may respond too (e.g. decline their own event).

### Task 2: Calendar routes

**Files:** Create `Spark_Core/backend/src/routes/workspace/schedule.ts` (registered from `src/routes/workspace/index.ts`); modify `src/routes/workspace/guard.ts` (whitelist), `Documents/context.md`. Test: `tests/workspace-schedule.test.ts`.

**Interfaces (base `/api/v1`):**
- `CalendarEvent = { id, title, description: string|null, location: string|null, startsAt, endsAt, timezone, status: "scheduled"|"cancelled", organizer: { id, displayName }, project: { id, key, name } | null, issue: { id, key, title } | null, attendees: Array<{ user: { id, displayName }, response: "pending"|"accepted"|"declined"|"tentative" }>, myResponse: <response> | null, canEdit: boolean, version }` (`canEdit` = actor is organizer or owner/admin and status scheduled).
- `Deadline = { kind: "task_due"|"sprint_end"|"milestone_due", date: "YYYY-MM-DD", title, project: { id, key, name, methodology }, issueId?: string, assignee?: { id, displayName } | null, sprintId?: string, milestoneId?: string }`.
- `GET /workspaces/{workspaceId}/calendar?from&to&tz` → `{ range: { from, to, tz }, events: CalendarEvent[], deadlines: Deadline[], truncated: { events: boolean, deadlines: boolean } }` (events by `startsAt`, deadlines by date then kind).
- `POST /workspaces/{workspaceId}/calendar-events` body `{ title, description?, location?, startsAt, endsAt, timezone, projectId?, issueId?, attendeeUserIds? }` → 201 `CalendarEvent` + `Location: /api/v1/calendar-events/{id}` + `ETag`.
- `GET /calendar-events/{eventId}` → `CalendarEvent` + `ETag`.
- `PATCH /calendar-events/{eventId}` (If-Match) → 200 `CalendarEvent`; `forbidden` → 403 `insufficient_role`; `cancelled` → 409 `event_cancelled`.
- `POST /calendar-events/{eventId}/cancel` (If-Match, no body keys allowed) → 200 `CalendarEvent`; `already_cancelled` → 409 `event_already_cancelled`.
- `PUT /calendar-events/{eventId}/attendees/me` body `{ response: "accepted"|"declined"|"tentative" }` → 200 `CalendarEvent`; `not_invited` → 403 `not_invited`; `cancelled` → 409 `event_cancelled`.
- Reads inside `guard.run` with explicit columns and explicit tenant filters; names via the coworker policy (fall back to "Former member" when unreadable, as M5 does).
