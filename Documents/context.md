# Spark product and architecture context

## Product goal

Spark helps startup communities discover each other, manage membership, collaborate, and moderate content. The first release must be a small, production-ready MVP: clear boundaries, reliable data, secure defaults, and enough automation to ship safely. Architecture exists to support product behavior; it must not add infrastructure before a real use case needs it.

All repository content must be English. This includes source code, identifiers, UI copy, documentation, comments, tests, fixtures, logs, errors, commit messages, pull-request text, generated artifacts, and new files.

## Current scope

Application code lives in `Spark_Core` as a pnpm workspace:

- `frontend`: Next.js 16, React 19, and TypeScript with UI/UX Pro Max design system (clean light SaaS theme, responsive navigation, production-ready login with OAuth suite, interactive Platform Governance Console at `/admin`, and landing page showcases).
- `backend`: Fastify and TypeScript, organized as a pragmatic Clean Architecture modular monolith. One build runs as three processes: the public API, a private auth process that alone holds the login database role, and a background worker that alone holds the `spark_worker` role and delivers outbox email over SMTP (credential security boundaries, not separate codebases). The worker role has no table privileges; it only executes the `spark.worker_*` functions.
- `infra`: local Redis and Mailpit (SMTP catcher on `127.0.0.1:1025`, inbox at `http://localhost:8025`) through Docker Compose, and local PostgreSQL on port 5432.

### Admin dashboards

Overview, Analytics, Reports and Communities in the staff console are dashboards (design: `Documents/product/2026-10-20-admin-dashboard-redesign-design.md`). Each page has its header, a row of trend cards (value, change chip, sparkline only where real history exists) and a 12-column bento grid of chart tiles above its existing working area. ## Technology choices

| Area | Choice | Reason |
| --- | --- | --- |
| Frontend | Next.js, React, TypeScript | Server rendering, routing, and accessible light-theme design tokens. |
| Backend | Fastify, TypeScript | Small runtime, schema-first HTTP APIs, Clean Architecture, and good performance. |
| Database | PostgreSQL through `pg` & Drizzle ORM | ACID transactions, strict schema constraints, Drizzle migrations (`0000`–`0031`), and RLS. |
| Security & Auth | Argon2id, SHA-256 bytea sessions | Robust password hashing, opaque session token management, and platform role RBAC. |
| Cache and limiter | Redis | Shared cache, distributed rate limits, and short-lived coordination. |
| Contracts | Fastify JSON Schema and OpenAPI | Runtime validation and generated API documentation without a premature shared package. |
| Tests | Vitest and focused integration tests | Fast feedback with real dependency coverage where it matters. |
| CI | GitHub Actions | `.github/workflows/ci.yml` runs the quality gate; remote protections are unverified. |

Use Node.js 26 and the pnpm version pinned by the repository. Prefer a modular monolith until measured scale or team ownership justifies another deployable service. Do not add Kafka, Kubernetes, Elasticsearch, a service mesh, or a graph database for the MVP.

## Architectural rules

The backend follows pragmatic Clean Architecture:

1. Domain code contains business rules and imports no framework or adapter.
2. Application use cases coordinate domain behavior through small ports.
3. Infrastructure implements database, cache, and external-service ports.
4. Presentation validates HTTP input and maps use-case results to HTTP responses.
5. The composition root wires concrete dependencies.

Use these layers when a feature has business behavior or an external dependency. A trivial endpoint does not need empty interfaces, factories, or directories solely to demonstrate a pattern. Full REST and dependency rules are defined in [REST and Clean Architecture compliance](architecture/rest-clean-compliance.md).

## Data and consistency

PostgreSQL is the source of truth. Every schema change uses a reviewed migration. Enforce invariants with constraints and transactions as well as application checks. Keep transactions short and use deterministic lock ordering. Multi-step writes that must commit together share one transaction. External side effects after commit use an outbox only when such a side effect exists.

Tenant-scoped tables include `tenant_id`; ownership relationships use composite constraints where appropriate. Runtime roles have least privilege. RLS is required when tenant data is introduced, with tests covering two tenants and reused pooled connections. Never claim ACID or tenant isolation from unit tests alone.

## Cache and rate limiting

Cache only measured read paths. Every cache entry needs an owner, scope, TTL, invalidation event, and fallback behavior. Cache keys include tenant and visibility scope. Invalidate after the database commit. Sensitive user responses default to `private, no-store`.

Redis backs rate limits for normal API traffic. Policies are route-specific and return `429` with `Retry-After`. Health endpoints are not rate limited. The service must remain correct during Redis failure; the documented route policy decides whether to fail open or closed.

## Security baseline

- Opaque sessions, secure cookies, session rotation, and server-side revocation when authentication is implemented.
- Per-resource authorization in application use cases and tenant filtering in database access.
- Strict request and response schemas, body-size limits, safe error responses, and no secrets or private payloads in logs.
- Explicit trusted proxies and HTTPS-only production origins.
- Parameterized queries, least-privilege database roles, dependency auditing, and pinned CI dependencies when CI is configured.
- Load balancers terminate TLS and forward only trusted proxy headers. Application nodes remain stateless.

## MVP user stories

### US-01: Discover startup communities

A visitor searches public communities by keyword and optional topic, location, or stage. Results use deterministic cursor pagination and show an empty state when no match exists. The API validates filters, limits page size, and may cache only public results. Search begins with indexed PostgreSQL queries; a separate search engine requires evidence that PostgreSQL is insufficient. Implemented in Phase 2 C1: `/communities` with search, topic, country and stage filters in the URL and "Show more" paging, and the community page `/communities/[slug]`.

### US-02: Request membership

An authenticated user requests access to a private community. Duplicate retries do not create duplicate requests. A community owner can approve or reject a pending request. Authorization, uniqueness, and state transitions are enforced transactionally. Implemented in Phase 2 C1: workspace owners and admins host communities (`/w/[slug]/communities`, `/w/[slug]/communities/new`); public communities are joined instantly, private ones by request and approval, hidden ones only when a manager adds a host workspace member; managers review requests and manage members and settings at `/communities/[slug]/manage`.

### US-03: Publish and discuss posts

A member creates a post and comments within an authorized community. Public, private, and hidden visibility rules apply consistently to lists and individual resources. Mutations use idempotency where network retries can duplicate work.

### US-04: Create a workspace and invite members

An owner creates a workspace and sends expiring, single-use invitations. Acceptance verifies the intended recipient and tenant. Workspace creation and initial ownership commit atomically.

### US-05: Manage tasks

Members create, assign, and move tasks. Concurrent updates use a version or conditional request so one update cannot silently overwrite another. Keyboard and mobile interactions remain usable. Implemented (M3): the project board at `/w/[slug]/p/[key]` (quick-add with an `Idempotency-Key`, drag and drop, keyboard moves, a "Move to…" menu, WIP limits refused with `409 wip_limit_reached`), a task drawer for editing, assigning and archiving with `If-Match` (a stale save gets `412` with the current task), the task history, and `?issue=<KEY>-<n>` deep links used by the assignment email. Issue versions are advanced by the write functions themselves (`version + 1`); the `maintain_record` trigger only checks that every update advances the version by exactly one. Implemented (M4, migrations `0023`–`0025`): Scrum sprint planning on the Backlog tab (one active sprint at a time, commitments snapshotted on start, unfinished work carried to the next sprint or the backlog on completion), the Waterfall Timeline (phase plan, milestones, variance against an immutable baseline that changes only by re-baselining with a reason), column names and WIP limits on the Settings tab (a limit below the cards in a column is refused), and a methodology switch wizard that remaps columns and tasks in one transaction, cancels planned sprints when leaving Scrum (their open tasks return to the backlog) and records methodology periods. Only owners, admins and the project lead may plan; other members see the plan read-only. Implemented (M5, migration `0026`): analytics computed on read for every active workspace member — the project Insights tab `/w/[slug]/p/[key]/insights` (done against the plan with a forecast, the selected methodology period's charts: Scrum burndown, velocity and commitment reliability; Kanban WIP, aging work and cycle time; Waterfall phase variance and milestone states; flow with methodology-switch markers, completion by member, overdue work) and the workspace page `/w/[slug]/insights` (per-project cards, members, activity calendar, overdue across projects). History is replayed from the task events by the SECURITY INVOKER `spark.insight_*` functions, so RLS still applies and every statement also filters by tenant and project; the pure rules (unit, plan status, forecast, reliability, scope creep, milestone state) live in `src/modules/work/domain/metrics.ts`. Plan status is decided from the percentages rounded to the one decimal the screens show. The burndown's ideal line starts from the committed work not done at the sprint's `started_at` (replayed, so day-1 work stays in it), and the Scrum forecast divides the active sprint's remaining work by the whole project's 14-day throughput. Member tables keep a departed assignee's work on its own row ("Former member" when the name is not readable). Measured on the seeded Northstar Labs workspace (`pnpm --filter @spark/backend db:seed:workspace`) at 180 days, every insight statement ran in under 20 ms without a sequential scan over tasks or task events, and every warm endpoint answered with p95 ≈ 52 ms or less (the maximum of 10 samples; the only slower call was a cold first request at 179 ms), so no index migration was added. The cost of `spark.insight_flow` grows with the range in days times the project's task events (for each day it looks at the project's events up to that day); if single projects grow large, rewrite it to replay incrementally rather than add an index. Implemented (M6): the workspace schedule `/w/[slug]/schedule` (every member) shows the viewer's local week from `GET /api/v1/workspaces/{workspaceId}/calendar` — team events (organizer, attendees and their answers, cancelled events kept and struck through) and derived deadlines (open task due dates, planned or active sprint ends, open milestone due dates) as chips — as a seven-day grid from 1280 px and an agenda below it; members create events, invitees answer Accept, Maybe or Decline, and the organizer, owners and admins edit (a new time resets answers to pending) and cancel with `If-Match`; the in-app notices `event_invited`, `event_rescheduled` and `event_cancelled` never go to the person who acted. Event writes are the `SECURITY DEFINER` `spark.ws_create_event`, `ws_update_event`, `ws_cancel_event` and `ws_respond_event` functions of migration `0027_schedule`; reads go through RLS. Sprint-end deadlines are UTC calendar days (sprints store their days as midnight UTC), like the sprint API; task due dates and milestone dates are calendar dates, and the deadline query runs against PostgreSQL in the database tests. Reminders (`event_reminders`) and email for events are not built.

### US-06: Notifications

Committed events create notifications through an outbox. The MVP may poll. Realtime delivery is added only when needed and always rechecks authorization before delivery. Implemented so far: an assignee gets an `issue_assigned` notification and one email; the worker rechecks membership, assignment, archive state and the email preference before sending. Starting a sprint gives each assignee of a committed task (except the starter) an in-app `sprint_started` notification, without email. Implemented (M7, migrations `0028`–`0029`): the inbox at `/notifications` (All and Unread tabs, 30 per page, a row opens its task, backlog, schedule week or members page and is marked read; "Mark all as read" sends the newest loaded row's creation time as `before`, so a notification that arrives meanwhile stays unread), the unread badge in the sidebar (polls every 30 seconds while the tab is visible, refetches on focus, "99+" above 99, a dot on the collapsed phone menu), and `/settings/notifications` (three email switches and the time zone). Leaving a workspace hides its notifications from the list, the count and mark-all without deleting them; rejoining shows them again. Notification reads and writes go through `SECURITY DEFINER` `spark.ws_*` functions that take the actor from the session (the table's only runtime grant remains the recipient's `SELECT`). Email: invitations and account mail always send; task-assigned, the daily due reminder and the Monday digest each have a preference (default on) and run in the user's `users.timezone`. The reminder and the digest are scheduled by the worker from a `scheduled_emails` ledger with one row per `(user, job, workspace or none, local period)`, so a period is sent once however many workers run; a missed 08:00 is made up later the same local day, never for a past day. Known limits: recipients are the unverified primary emails until Phase 3 (email verification), so a person can receive mail at an address they never confirmed; delivery is at least once (a worker that dies between the SMTP send and recording it repeats the email after the 5-minute lease); each job sends 5 emails a minute (about 300 an hour), so a large population is delivered slowly and what is still unsent at local midnight is dropped; the digest's "completed last week" credits the assignee in the done snapshot rather than the person who moved the card; unread counts are capped at 100 and the inbox polls instead of pushing.

### US-07: Report content

Users report content without revealing reporter identity to ordinary members. Moderators see only their authorized queue. Every moderation action records actor, target, reason, and timestamp.

Mentor matching, file uploads, rich realtime collaboration, and AI summaries are post-MVP work.

## Operational targets

- Keep the frontend initial route small and lazy-load noncritical features.
- Define latency and error targets per implemented endpoint; do not invent global scale claims.
- Use horizontal application replicas behind a load balancer only when deployment needs them.
- `GET /health` reports process health. Startup fails when required dependencies cannot connect. Add a separate readiness endpoint only when a deployment platform requires it.
- Backups, restore tests, failover, observability, and alerts are deployment work and must be verified in the target environment.

## Delivery pipeline

The repository pipeline is intentionally small:

1. Install dependencies from the frozen lockfile.
2. Run lint, type checks, focused tests, and production builds. Add contract, architecture, or live dependency gates when implemented behavior needs them.
3. Run dependency auditing.
4. Obtain independent review for risky changes such as authentication, RLS, migrations, CI policy, or complex transactions.
5. Merge only the tested commit after required review and checks pass.
6. Deploy the same built artifact, run migrations as a separate controlled step, and smoke-test the release.

Details live in [automation](automation/README.md). Remote branch rules, CODEOWNERS, environments, and deployments are not active until configured and verified on the hosting platform.

## Definition of done

A story is done when its acceptance criteria work, API contracts match behavior, authorization and data invariants are tested at the right boundary, migrations are reversible or have a documented recovery path, logs expose no sensitive data, and applicable repository checks pass. Report the exact commands run and any operational limitations.

## Implementation order

1. Keep the local foundation simple and reproducible.
2. Implement authentication and tenant boundaries.
3. Deliver community discovery and membership.
4. Add posts, workspaces, tasks, and moderation.
5. Measure before adding cache layers, realtime infrastructure, or new services.

Before coding a feature, define its contract, authorization rule, transaction boundary, cache behavior, failure behavior, and tests. Choose the smallest design that satisfies those requirements.
